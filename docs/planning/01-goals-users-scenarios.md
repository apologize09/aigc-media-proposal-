# 1. 项目目标、目标用户、核心使用场景

## 1.1 项目要解决的问题

内部团队接到客户需求和素材之后，需要产出三份彼此一致的结果：

1. 一份客户能看的专业 HTML 提案。
2. 一份只在内部使用的成本与利润核算。
3. 一份审核通过后可以执行的任务拆解。

今天这三份结果如果靠聊天记录、散落素材和手工排版拼出来，案例难追溯、报价和方案容易对不上、改一版就要重做整页。系统要把这条链路收成一个可编辑、可预览、可审核、可留版本的内部流程。

这句话是对已确认需求的归纳，不是额外的商业承诺。

## 1.2 项目目标

### 已确认的产品目标

- 内部人员在 Web 系统中完成从需求录入到审核交付的主路径。
- 客户看到的交付物是 HTML 提案，内容覆盖创意、案例、视觉风格、分镜参考、制作流程、报价、项目排期。
- 案例可以来自客户素材，也可以来自全网搜索到的图片、视频和创意案例。
- 提案按模块编辑，而不是只重新生成一整段不可拆的正文。
- 同一项目内能做成本利润核算，并能生成执行任务。
- 未审核通过的方案不能作为对客户的正式交付。这一点来自「审核后交付」。

### 合理假设的成功标准（待确认后才作为验收指标）

下列数字都还没有业务确认，不能当作本期 KPI。审查时只需要决定要不要测量、以及目标值是多少。

- 从「需求与素材齐备」到「可送审的提案初稿」的人工整理时间是否下降。
- 送审稿中，报价模块与内部报价行是否一致。
- 已交付版本是否都能回溯到当时的 HTML 快照、选用案例和审核记录。
- 搜索结果是否经过人工选用后才进入客户可见提案。见第 3 篇中的假设规则 R-A1。

### 非目标

这些不是本期要证明的事：

- 用系统替代剪辑、设计和投放工具。
- 自动向客户报出可成交价格。模型不准自行编造报价数字，见第 4 篇决策 D3。在费率表确认之前，报价格由内部人员填写。
- 把全网内容爬进自有媒体库后任意再分发。搜索是「找参考并经人工选用」，不是自建抓取平台。
- 对外售卖多租户 SaaS。

## 1.3 目标用户

### 已确认

- 主要使用者是公司内部人员。系统形态是内部 Web 系统。
- 客户是需求与素材的提供者，也是 HTML 提案的接收者。
- 客户不登录。交付方式是链接（Q1，2026-10-16）。客户账号和在线批注不在 MVP。

### 已确认的内部角色（Q4，2026-10-16）

系统角色为三种，一个人可以兼任。成本与利润另用财务可见开关，不单设第四种角色。

| 角色 | 在系统里做什么 |
| --- | --- |
| 管理员 | 开通和停用账号、分配角色和财务开关。管理员可见全部项目 |
| 方案编辑 | 在自己参与的项目里录入需求、上传素材、确认分析、选用案例、编辑提案、维护任务、填写成本与报价（须另有财务可见）、送审、创建或撤销链接 |
| 审核人 | 对自己参与的项目里已送审的快照通过或退回。审核动作不改写提案正文 |

项目按参与人隔离：不是参与人、也不是管理员的账号，看不见该项目。本次没有要求「编辑不能审核自己送出的快照」。一个人同时有方案编辑和审核人时，可以审自己送出的快照。

### 客户侧（Q1 已确认）

客户不登录。内部审核通过后，用可撤销的链接把冻结的 HTML 交给客户。链接指向发布当时的快照。新版本使用新链接，旧链接仍打开旧快照。

## 1.4 核心使用场景

每个场景只描述已确认流程里的一段。参与者使用上一节已确认的角色名。

### 场景 A：收下需求并得到可编辑初稿

- 触发：内部人员拿到客户需求说明和素材。
- 路径：建立客户与项目 → 写入需求正文 → 上传素材 → 发起分析 → 人工确认或改正 → 由豆包在生成提案模块时自行联网搜索并匹配图片、视频和创意案例 → 对工具返回的真实地址转存 → 得到可编辑草稿。
- 成功：项目里有一份由模块组成的草稿，预览能看到已确认内容类型（创意、案例、视觉风格、分镜、流程、报价、排期）。报价格可以为空，等待人工填写。
- 搜索无结果或 AI 失败时，项目仍可保存，允许手工补链接、手工写模块。见第 3 篇异常。

### 场景 B：把初稿改成能送审的提案

- 触发：草稿的文案、案例或结构不达标。
- 路径：按模块改文案、隐藏或调整顺序、替换图片或视频、必要时只重做某一个模块 → 预览 → 再改。
- 成功：编辑的是模块内容，预览同步变化；客户素材和网络参考在提案里可区分。区分方式是假设 R-A2，待确认。
- 不在本场景：直接把整页改成不受约束的 HTML 字符串。整页源码编辑不在 MVP。

### 场景 C：核算成本与利润，并写进对客报价

- 触发：方案范围足够判断工作量，需要内部核算。
- 路径：录入成本项 → 录入对客报价项 → 选择哪些报价项出现在 HTML 的报价模块。
- 成功：有财务可见的内部人员能看到成本和报价。利润区显示「未配置」，因为本期没有公式（Q5，2026-10-16）。客户 HTML 只含被选入提案的报价，不含成本明细和利润。
- 本期不预置币种、税率、成本科目和费率表。金额只保存人工录入的结果。

### 场景 D：拆执行任务

- 触发：方案和报价范围需要变成可执行工作。
- 路径：手工添加任务 → 改标题、说明、负责人和日期 → 确认任务列表。
- 成功：任务挂在项目上，状态能区分草稿和已确认。
- 已确认：不做行业模板，任务以手工为主（Q6，2026-10-16）。MVP 不按业务类型自动生成任务包。

### 场景 E：审核后交付

- 触发：编辑认为提案、报价和任务可以送审。
- 路径：发布一份不可变快照 → 提交审核 → 审核人只审这份快照 → 通过后生成交付链接；退回则回到编辑，改完重新发布再审。
- 成功：客户打开的是审核通过的那一版 HTML，而不是之后又改过的草稿。
- 已确认：先审核，后交付。单人审核即可通过（Q7）。链接可撤销；旧链接继续指向旧快照（Q8）。

### 场景 F：交付后继续迭代

- 触发：客户反馈要改文案、案例、报价或排期。
- 路径：在不改写已交付快照的前提下产生新版本 → 编辑 → 手工调整报价和任务 → 再次单人审核 → 用新链接交付。
- 成功：旧链接仍打开旧快照；新链接指向新快照。这是 Q8 的结论。

## 1.5 场景之间的数据关系

三个输出必须指向同一项目、同一提案版本，避免「客户看到的报价」和「内部任务所依据的方案」不是一版。

```text
项目
├── 需求正文 + 客户素材
├── AI 分析（可多版，有当前确认版）
├── 搜索与选用的案例
├── 提案草稿 ──发布──▸ 提案快照（客户 HTML 的唯一来源）
├── 成本项（仅内部）
├── 报价项 ──选择后投影──▸ 快照中的报价模块
├── 利润（仅内部；本期无公式，界面保持未配置）
├── 执行任务（关联送审或交付时所依据的快照）
└── 审核记录 + 交付记录（只绑定快照，不绑定草稿）
```
